# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev          # Next.js dev server (Turbopack)
npm run build        # production build
npm run lint         # eslint (flat config: next core-web-vitals + typescript)
npx tsc --noEmit     # typecheck
npx eslint <file>    # lint a single file
npm run typecheck    # tsc --noEmit
npx convex dev       # push convex/ to the dev deployment + regenerate convex/_generated (keep running while developing)
scripts/test-check-no-ai.sh   # test the AI-attribution patterns
```

There is no test suite. Verify changes with `tsc`, `eslint`, `npm run build`, and by running the app. `npm run lint` still reports older `no-explicit-any` errors, so make sure you do not add new ones.

Env vars (in `.env.local`, written by `npx convex dev`): `CONVEX_DEPLOYMENT`, `NEXT_PUBLIC_CONVEX_URL`, `NEXT_PUBLIC_CONVEX_SITE_URL`. Convex Auth needs `JWT_PRIVATE_KEY`, `JWKS`, and `SITE_URL` on the Convex deployment itself (set with `node scripts/set-convex-auth-keys.mjs [--prod] --site-url=<url>`).

## What the app does

Internal Next.js 16 (App Router) + Convex app for an SPPG (school-meal kitchen) operator. The user uploads an Excel "RAB" workbook (one sheet per day), items are grouped by supplier, and one PDF invoice per supplier is rendered and saved to history. Users need an admin-approved paid subscription; admins manage subscriptions, users, appeals, and plan settings under `/admin`.

UI copy, toasts, and most code comments are in Bahasa Indonesia — keep new strings in Indonesian.

## Architecture

### Backend: Convex
The app moved from Supabase to Convex on 2026-10-28 (the Supabase project was restricted after its storage quota filled up). Everything lives in `convex/`: `schema.ts`, one file per area (`users.ts`, `subscriptions.ts`, `admin.ts`, `appeals.ts`, `invoices.ts`), and Convex Auth in `auth.ts`. The one-time Supabase import scripts were removed after the import; `docs/migrasi-convex.md` records what moved and how the deployments are set up. `convex/_generated/` is generated by `npx convex dev` and committed.

- Column names stay snake_case and timestamps are ISO strings, as in the old Supabase tables, so API response shapes did not change. Documents are returned with `id` instead of `_id` (`withId` in `convex/lib/auth.ts`).
- **Every public Convex function checks access itself** with `requireUser` / `requireAdmin` (or `requireInvoice` for ownership) from `convex/lib/auth.ts`, because Convex functions can be called directly from the internet. Role is read from the `users` table, never from args or the token. Errors go through `fail(code, message)`, which `lib/convex/server.ts:errorResponse` maps to 401/403/400/404.
- Login is Convex Auth with the `Password` provider. Passwords are hashed with bcrypt (sync `bcryptjs`; the async API uses `setTimeout`, which mutations reject) so the bcrypt hashes imported from Supabase `auth.users` keep working. The minimum is 6 characters (`MIN_PASSWORD_LENGTH`). `profile()` only takes email and name from the sign-up form; role and status are always the defaults. Admin password reset is the `admin.resetPassword` action (`modifyAccountCredentials`).
- The Next.js API routes are kept as thin wrappers: they call Convex with the user's token through `convexQuery` / `convexMutation` / `convexAction` in `lib/convex/server.ts`. PDF rendering stays in Next.js route handlers.

### Auth gating
`middleware.ts` (`convexAuthNextjsMiddleware`) is the single source of truth for page access, using one query, `users.accessState`: unauthenticated → `/login`, suspended/banned (non-admin) → `/blocked`, no active subscription (non-admin) → `/subscribe`, `/admin/*` requires `role === 'admin'`. The middleware also proxies `/api/auth` (sign-in, sign-out, token refresh) to Convex, so keep `/api` in its matcher. It skips its own checks for the other `/api/*` routes, which rely on the checks inside the Convex functions.

Client-side sign-in/out uses `useAuthActions()` from `@convex-dev/auth/react`. `components/auth/auth-client.ts` holds `useLogout()` and `registerSession()`. `components/auth/session-guard.tsx` enforces single-active-session (localStorage `invoice_session_id` vs `users.active_session_id`, polled via `/api/session`) and idle logout.

### Excel → items (`lib/excel/parser.ts`, `lib/excel/normalizer.ts`)
- Parsing runs **in the browser** (`components/excel/excel-uploader.tsx` → `parseExcelWorkbook`). The server only receives the already-parsed items.
- `parseExcelWorkbook` parses every sheet; `parseSheetName` derives date / date range / category (`OPS`, `OPS GALON`) / tahap from Indonesian sheet names like `"21 JAN 2026 DONE"`.
- Header row is detected by column aliases (URAIAN, QTY, HARGA, SATUAN, TOTAL, SUPPLIER). Numbers use Indonesian separators (`parseIndonesianNumber`).
- Rows with an empty SUPPLIER cell are attributed by looking ahead to the next `NO REK. <account> <bank>` line.
- `normalizeItemName` rewrites item names (title case, units, `isi N` parentheses, stripping quality/packaging notes). Changes here affect preview, PDF, and DB.

### Suppliers — keep these in sync
Suppliers are a hardcoded, authorized list. An unknown supplier must **not** fall back to a default template; it raises `UnrecognizedSupplierError` and is reported back to the user. Adding or renaming a supplier touches:
- `data/cv-reference.ts` — `supplierMapping` (bank account, `legacyBankAccounts`, address, theme color) and `getSupplierConfig` (legacy name aliases, account-number matching)
- `lib/pdf/utils.ts` — `SupplierTemplateKey` + `getSupplierTemplateKey` (keyword matching; order matters, e.g. SUSILO is checked before YUWONO)
- `lib/validators.ts` — `normalizeSupplierName`
- `lib/pdf/templates/index.ts:renderSupplierTemplate` — the only supplier → template map, used both for the first generation and for re-rendering in `/history` (both through `pdf-generator.ts`)
- `lib/pdf/templates/*-template.tsx` and `public/assets/<supplier>/`

Some suppliers share a template (Nusantara Food and Susilo Widyono both use `sekar-wijayakusuma-template.tsx`, differing by `signatureName`).

### PDF generation
- PDFs are rendered **server-side only** with `@react-pdf/renderer` (listed in `serverExternalPackages` in `next.config.ts`). Assets are loaded from disk via `getAssetPath`.
- Every PDF embeds the logo/signature/stamp PNGs in full. Keep those PNGs at ~300 dpi of their display size: logo box 55pt → ~230 px, signature box 90pt → ~375 px, stamp 50pt → ~210 px. A 1000 px logo once made every PDF ~800 KB, and storing them pushed Supabase storage (free tier: 1 GB) over quota, which restricts the whole project, login included.
- Main path: client → `POST /api/generate-pdf` → `generateInvoicePDFsWithNumbers` → PDFs returned as base64 in JSON, and the items written to `invoice_history` + `invoice_items`. PDFs are **not** uploaded to storage: `/history` re-renders them from `invoice_items` through `GET /api/invoices/[id]/pdfs` → `generateInvoicePDFsFromItems` (invoice number, date, customer name, and items are all in the DB). Do not start storing PDFs again. The client decodes them for preview and download through `lib/pdf/download.ts` (single file, ZIP via `jszip`, or merged via `pdf-lib`). Keep that module free of `@react-pdf/renderer` imports so the browser never loads the renderer.
- Document variants: `'tagihan'` (title TAGIHAN, signature, no LUNAS stamp) and `'kwitansi'` (title KWITANSI, no signature, customer label "Pembayaran"). Rules live in `lib/pdf/doc-variant.ts` (client-safe, imported by both templates and `app/upload/page.tsx`): Tambak/Sumpiuh/Buayan always use these variants; other customers only for invoices dated from 2026-10-12 (`ALL_CUSTOMER_VARIANTS_FROM`). Before that they get the legacy `'faktur'` (title FAKTUR, signature + LUNAS stamp, no toggle, batch prefix "Kwitansi"). Each template calls `resolveDocType(customerName, invoiceDate, documentType)` itself, so the first generation and the `/history` re-render both follow the cutoff. `documentType` undefined means TAGIHAN. The variant is toggled in `components/invoice/fullscreen-pdf-preview.tsx` (hidden when every selected sheet is legacy); the first generation is TAGIHAN and saves history, and switching re-calls `/api/generate-pdf` with `saveHistory: false`. Batch/file names are prefixed "Tagihan"/"Kwitansi" to match. Helpers: `getInvoiceTitle`, `getInvoiceNumberLabel`, `shouldHideSignature`, `shouldShowStamp`, `getCustomerLabelPrefix` in `lib/pdf/utils.ts`.
- The number/date header box (No. Tagihan/Kwitansi + Tanggal) is the shared `lib/pdf/templates/invoice-meta.tsx` (`InvoiceMeta`), used by all five templates and colored with each supplier's theme. Change header layout there, not in each template.
- Invoice numbers are `#0001`-style (`generateInvoiceNumber`), with no prefix. The user enters the starting number in `app/upload/page.tsx`, numbering continues sequentially across the selected sheets, and the starting number is kept in localStorage. Upload-flow state, including the per-variant PDF cache, lives in `useState` in that page.
- Customer ("Tagihan Kepada"): the SPPG name defaults from the workbook filename (`extractSppgNameFromFilename` in `lib/excel/normalizer.ts`, e.g. `"RAB SPPG Tambak (3).xlsx"` → `"Tambak"`) and can be overridden per supplier (`customerNames` record in `pdf-generator.ts`, falling back to `customerName`). Templates default to `'SPPG Pandansari'`. It is persisted in `invoice_items.customer_name`.
- Editing in `/history` → `PATCH /api/invoices/[id]` → `invoices.update` applies item edits/inserts/deletes (items must belong to that invoice) and recomputes totals and the `suppliers` list. It renders nothing; the next preview/download re-renders from the DB.
- `invoice_items.position` is the row order from Excel (and from the Supabase export for old rows). `invoices.get` sorts by supplier, then `position`, so re-rendered PDFs keep the original item order. New items get the next position.

### Data
Convex tables (`convex/schema.ts`): `users` (Convex Auth's table plus the old `profiles` columns), Convex Auth's own `auth*` tables, `subscriptions`, `subscription_config` (singleton), `invoice_history` (with a denormalized `suppliers` array so the list never reads items), `invoice_items`, `login_history`, `appeals`. `legacy_id` holds the Supabase UUID for imported rows. File storage is only used for payment proofs (`subscriptions.payment_proof_id`); `/api/admin/payment-proof?path=` takes that storage id. Payment-proof files from Supabase were not migrated (`legacy_payment_proof_path`). Free plan limits: 0.5 GB database, 1 GB files, 1 GB/month database I/O, so avoid queries that read every `invoice_items` row. Shared types are in `types/index.ts`.

## Conventions
- 4-space indent, single quotes; semicolon usage varies, so match the file you're editing.
- API responses: `{ success: true, data }` on success, `{ error, message? }` on failure. API routes that read auth use `export const dynamic = 'force-dynamic'`.
- UI: shadcn/ui (`components/ui/*`), `lucide-react` icons, `sonner` toasts (`toast.success/error/warning`). Currency/date formatting goes through `lib/pdf/utils.ts` (`formatCurrency`, `formatNumber`, `formatDate`).
- Logo masters and usage rules live in `docs/brand/` (see its README). The app icons are `app/icon.svg`, `app/favicon.ico`, and `app/apple-icon.png`.

## Git workflow

- Branch from `main` (`feat/…`, `fix/…`, `chore/…`, `docs/…`), one topic per PR. Commit messages use Conventional Commits in Bahasa Indonesia.
- CI (`.github/workflows/ci.yml`) runs typecheck and a production build on every PR and push to `main`. Vercel deploys `main` to production.

### No AI attribution

Commits, PRs, and comments are recorded under the human who made them. No AI account may appear as an author, a committer, or in the repo's Contributors list. Never write:
- trailers such as `Co-Authored-By: Claude <noreply@anthropic.com>`, `Claude-Session: …`, `Assisted-by: …`, or the equivalent from other agents (Codex, Copilot, Cursor, Gemini, Aider, Devin, Jules, Amp, Warp, and so on);
- footers such as `🤖 Generated with Claude Code` or `Generated by Copilot`, or agent session links;
- an AI agent or bot as the commit author or committer.

Claude Code attribution is turned off in `.claude/settings.json`. The rule is enforced in layers:

| Layer | Checks | When |
| --- | --- | --- |
| `.githooks/commit-msg` | Commit message | Every `git commit` |
| `.githooks/pre-push` | Author, committer, and message of every pushed commit | Every `git push` |
| `.github/workflows/no-ai-attribution.yml` | Same as pre-push, plus PR title and body | Every PR and push to `main` |

`npm install` turns the hooks on through the `prepare` script. Without that, run `git config core.hooksPath .githooks` once per clone. If a check fails, fix the commit (`git commit --amend`, or `git rebase -i origin/main` for older commits) instead of skipping it with `--no-verify`. CI rejects it anyway. Patterns live in `scripts/check-no-ai.sh`, and examples live in `scripts/test-check-no-ai.sh`.

GitHub counts `Co-authored-by` trailers toward the Contributors list, so one AI trailer on `main` is enough to put the agent there. On 2026-10-24 the history of `main` was rewritten to remove the old trailers; file contents, authors, and dates did not change. A clone made before that date must run `git fetch origin && git reset --hard origin/main` instead of `git pull`, or the old commits come back.
